Sam & Co, barbers

This page is deliberately plain. It has no framework, no build step and no styling worth mentioning, because the thing being demonstrated is that a shop does not need any of that: one <script> tag, and a visitor can both talk to somebody and book a time.

One tag, not two. Booking is reached through the widget the shop already embeds — the “Book” button in the panel header. That is 20-06’s embed decision, settled on product grounds rather than packaging ones: booking has to work from Telegram, MAX and SMS as well, where there is no widget at all, so a booking-only embed would be the one shape the product model rules out.

What the shop pastes

<script src="https://…/ago-chat.js"
        data-site="demo_site"
        data-api="http://localhost:5009"
        data-booking="demo-barbershop"
        data-booking-api="http://localhost:5011"
        async></script>

Two keys, because there are two products with two databases and two tenants (adr/0027). The shop’s own page is the one place that legitimately knows about both — it bought both. Putting AGO Calendar’s key into AGO Chat’s widget-config response would have saved a line here and put one product’s identifier inside the other product’s domain.

data-booking-api has no built-in default, unlike data-api: AGO Calendar is a separate deployable a shop may not have at all, so a default would be this bundle asserting an address for a product that might not be running. Leave either attribute out and there is no Book button and no request to AGO Calendar.

Running it against the local stack

This page is served from a different origin than either API, on purpose — the two-layer CORS model is only exercised by a genuinely cross-origin page. The tenant’s allowed_origins must contain whatever origin serves this file, or the browser refuses the response and the panel says booking is unavailable. See ago-root/docs/runbooks/local-dev.md.
